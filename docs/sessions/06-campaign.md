# Session 06 — Campaign, persistence and validation

## Prompt

Start only after the first completed fight is approved. Read the earlier session handoffs. Ask for the remaining campaign scope: number of opponents, desired total play length, character theme/story tone and win/loss progression. Do not invent a large roster. Build agreed original opponents with distinct fighting personalities, readable tells and escalating tactical lessons. Reuse the proven fighter system, ring and asset pipeline. Create entrances, transitions and victory moments while preserving continuous control during fights.

Add versioned local save/settings persistence and a clear restart path. Complete controller disconnect/resume handling, keyboard/pointer fallback, audio settings, reduced-motion and responsive layout. Measure laptop performance and only claim mobile support after testing appropriate devices. Adapt resolution/effects where needed. Use bounded visual review, meaningful combat tests and actual playthroughs rather than endlessly polishing isolated screenshots.

## Acceptance

- Progression, retries and saves behave consistently across reloads.
- Opponents differ mechanically and visually; difficulty remains fair with rotary controls.
- No stale hardware event affects the next encounter.
- Full campaign can be completed with fallback controls and available physical hardware.
- Performance and browser/device limits are documented; no fabricated benchmark.

## Handoff

Final run instructions, deployment options if requested, remaining limitations and an evidence-based release checklist. Publishing and remote repository creation require a user request; this session does not assume them.
